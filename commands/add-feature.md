# 新機能追加/アップデートワークフロー

機能 `$ARGUMENTS` を以下の手順で実装してください：

## 1. 要件の明確化（Interview Phase）

**まず私にインタビューしてください**。AskUserQuestionツールを使用して以下を確認：

- 技術的実装の詳細
- UI/UXの期待値
- エッジケースの処理
- パフォーマンス要件
- セキュリティ考慮事項
- トレードオフの選択

すべてカバーしたら、完全な仕様を `SPEC.md` に書いてください。

## 2. 探索と計画（Plan Mode）

### 2.1 既存コードの理解
- 関連する既存機能を探索
- アーキテクチャパターンを理解
- 再利用可能なコンポーネントを特定

### 2.2 実装計画の作成
以下を含む詳細な計画を作成：
- 変更が必要なファイルのリスト
- 新規作成が必要なファイル
- データベーススキーマの変更
- API エンドポイントの変更
- 依存関係の追加
- テスト戦略

計画を私に提示して承認を得てください。

## 3. 実装（Normal Mode）

### 3.1 データベース層
マイグレーションが必要な場合：
```bash
npm run migration:generate --name=<MigrationName> --prefix fondesk-api
```

マイグレーション実装時の確認事項：
- [ ] up() と down() の両方を実装
- [ ] インデックスを適切に設定
- [ ] 外部キー制約を適切に設定
- [ ] 本番環境への影響を考慮（ダウンタイム、ロック時間）
- [ ] データ移行が必要な場合は安全に実装

### 3.2 ビジネスロジック層
Service、Entity、DTOを実装：
- TypeORMのベストプラクティスに従う
- トランザクションを適切に使用
- エラーハンドリングを徹底
- ログを適切に出力

### 3.3 API層
Controller を実装：
- RESTful な設計
- 適切な HTTP ステータスコード
- Swagger ドキュメント
- バリデーション

### 3.4 統合
- 既存機能との統合を確認
- サイドエフェクトを確認
- パフォーマンスへの影響を確認

## 4. テスト戦略

### 4.1 ユニットテスト
```bash
# 変更したファイルのテスト
npm run test --prefix fondesk-api -- <pattern>

# カバレッジ確認（100%を目指す）
npm run test:cov --prefix fondesk-api -- <pattern>
```

### 4.2 統合テスト
必要に応じてE2Eテストを追加：
```bash
npm run test:init --prefix fondesk-api
```

### 4.3 手動テスト
以下をテスト：
- [ ] ハッピーパス
- [ ] エラーケース
- [ ] エッジケース
- [ ] パフォーマンス
- [ ] セキュリティ

## 5. ドキュメント

以下を更新：
- [ ] API ドキュメント（Swagger）
- [ ] README（必要な場合）
- [ ] CLAUDE.md（新しいパターンやルールがあれば）

## 6. レビューとコミット

### 6.1 セルフレビュー
- [ ] コードの品質
- [ ] テストカバレッジ
- [ ] パフォーマンス
- [ ] セキュリティ
- [ ] 既存機能への影響

### 6.2 サブエージェントレビュー（推奨）
```
サブエージェントを使ってこの実装をレビューして：
- セキュリティ面
- コード品質
- テストの妥当性
```

### 6.3 コミット
```
🚀 [機能名]を追加

または

📈 [機能名]を改善
```

## 7. プルリクエスト作成

```bash
gh pr create --title "[機能名]" --body "$(cat SPEC.md)"
```

## 注意事項

- 過度に複雑にしない（YAGNI原則）
- 既存パターンに従う
- 段階的にコミット（大きすぎるPRを避ける）
- 本番環境への影響を常に考慮
