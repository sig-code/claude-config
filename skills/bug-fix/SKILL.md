# バグ修正・インシデント対応スキル

## 原則

1. **本番インシデントは影響の最小化が最優先**: 原因究明より先にロールバック・機能一時停止でユーザー影響を止める
2. **再現してから直す**: 再現手順を確立してから原因を探る。修正は1箇所ずつ検証する
3. **直したら再発防止まで**: バグを再現するテストの追加・監視改善・根本原因のドキュメント化までが完了条件

## Bugsnag トリアージ（「エラー見て」系の依頼）

1. `bugsnag_get_current_project` で対象プロジェクトを確認（指定がなければ fondesk 系）。横断確認は `bugsnag_list_projects`
2. `bugsnag_list_project_errors` で直近（デフォルト24時間、指定があればその期間）を取得。発生件数順と初回発生日時順の両方を見る
3. 分類:

| 分類 | 判定基準 | アクション |
|---|---|---|
| 🆕 新規 | 初回発生が対象期間内 | 最優先で深掘り |
| 📈 急増 | 既存だが件数が通常比で顕著に増加 | デプロイ・外部要因との相関確認 |
| 🔁 再発 | 過去に fixed にしたものが再発生 | 修正の見直し |
| 💤 既知・定常 | 以前から一定頻度で発生 | 報告のみ（対応不要の根拠を添える） |

4. **深掘りは 🆕新規 と 📈急増 のみ**: `bugsnag_get_error` → `bugsnag_get_events_on_an_error` でスタックトレース・影響ユーザー数・発生環境を確認し、該当コード箇所と直近コミット・デプロイの関連を調べる
5. 報告テンプレ:

```markdown
## Bugsnag トリアージ結果（対象: <プロジェクト> / 期間: <期間>）

### 要対応 🚨
| エラー | 分類 | 件数/ユーザー数 | 推定原因 | 関連コード |
|---|---|---|---|---|

### 経過観察 👀
- <エラー>: <理由>

### 対応不要（既知・定常） ✅
- <エラー>: <根拠>
```

## インシデント対応プレイブック

- **P1（サービス全停止）**: [0-5分] 状況確認・ログ取得 → [5-15分] 影響最小化（ロールバック/機能停止） → [15-60分] 原因特定・修正 → [60分〜] RCA・再発防止
- **P2（機能一部不具合）**: 影響ユーザーの特定 → 回避策があれば周知 → 修正PR → RCA

## インシデントレポート（RCA）テンプレ

```markdown
## インシデントサマリー
- **発生日時**: YYYY-MM-DD HH:mm
- **影響範囲**: [ユーザー数/機能]
- **原因**: [一行で]
- **TTD**: X分 / **TTR**: X分

## タイムライン
- HH:mm 異常検知 / HH:mm 原因特定 / HH:mm 修正デプロイ

## 根本原因
[5-Why で症状ではなく根本原因まで掘る]

## 再発防止策
- [ ] バグを再現するテスト追加
- [ ] 監視・アラート改善
- [ ] ドキュメント更新
```

## アンチパターン

- ❌ 全エラーを深掘りして時間を溶かす → 深掘りは新規・急増のみ
- ❌ スタックトレースの生ログを長々貼る → 発生箇所・条件の要点に要約
- ❌ 症状だけ修正して根本原因を放置 → 5-Why で根本まで追い、再発防止テストを追加
- ❌ 本番でデバッグ → ローカル/ステージングで再現
