# デバッグ・インシデント対応スキル

## 🎯 ゴール

**再現 → 特定 → 修正 → 再発防止** の最短ルートで解決する。感覚的なデバッグをやめ、仮説を立てて検証する。

## 🚨 最重要ルール

1. **まず再現させる**: 再現できないバグは直せない。再現手順を確立してから原因を探る
2. **仮説を立ててから調査**: 「何かおかしい」ではなく「〇〇が原因なら〇〇のはず」という仮説で動く
3. **本番インシデントは影響の最小化が最優先**: 原因究明より先にユーザー影響を止める
4. **直したら再発防止策まで**: テスト追加・ドキュメント更新・監視追加
5. **エラートラッキングは bugsnag-triage スキルと連携**: Bugsnag 上のエラー確認はそちらを使用

## 🔍 デバッグフロー

### Step 1: 症状を正確に把握する

```
- エラーメッセージの全文（スタックトレース含む）
- 発生タイミング・頻度・条件（特定ユーザーのみ? 全員?）
- 最後に変更したコード・インフラ（git log, デプロイ履歴）
- 影響範囲（機能・ユーザー数・データ）
```

### Step 2: 仮説を立てる（3つ以内）

```
仮説1: [原因候補] → 確認方法: [ログ/テスト]
仮説2: [原因候補] → 確認方法: [ログ/テスト]
仮説3: [原因候補] → 確認方法: [ログ/テスト]
```

確率が高い順に検証。1つ検証したら次に進む（複数同時に変えない）。

### Step 3: 最小再現コードを作る

バグを最小構成で再現できれば、原因が特定しやすい。

```bash
# 不要な要素を除いた最小のテストケース
npm test -- --testNamePattern="問題のある処理"
```

### Step 4: 修正と検証

- 修正は1箇所ずつ（複数同時変更しない）
- 修正後に同じ手順で再現しないことを確認
- エッジケースも確認

### Step 5: 再発防止

```
- [ ] バグを再現するテストを追加した
- [ ] 根本原因をドキュメント化した
- [ ] 同様のバグが他にないか確認した
- [ ] 監視・アラートを改善した
```

## 📋 インシデント対応プレイブック

### P1（サービス全停止）

1. **[0-5分]** 状況確認・エラーログ取得
2. **[5-15分]** 影響の最小化（ロールバック/機能一時停止）
3. **[15-60分]** 根本原因特定・修正
4. **[60分〜]** RCA 作成・再発防止

### P2（機能一部不具合）

1. 影響ユーザーの特定
2. 回避策があれば周知
3. 修正 PR 作成
4. RCA 作成

### インシデントレポートテンプレート

```markdown
## インシデントサマリー

- **発生日時**: YYYY-MM-DD HH:mm
- **影響範囲**: [ユーザー数/機能]
- **原因**: [一行で]
- **TTD (Time to Detect)**: X分
- **TTR (Time to Resolve)**: X分

## タイムライン
- HH:mm 異常検知
- HH:mm 原因特定
- HH:mm 修正デプロイ

## 根本原因
[技術的な根本原因]

## 再発防止策
- [ ] テスト追加
- [ ] 監視追加
- [ ] ドキュメント更新
```

## 🔬 5-Why 分析

```
Why 1: なぜエラーが発生したか？ → [回答]
Why 2: なぜ[回答1]が起きたか？  → [回答]
Why 3: なぜ[回答2]が起きたか？  → [回答]
Why 4: なぜ[回答3]が起きたか？  → [回答]
Why 5: なぜ[回答4]が起きたか？  → [根本原因]
```

## 🚫 アンチパターン

| ❌ | ✅ |
| --- | --- |
| 再現せずに修正開始 | 再現手順を確立してから修正 |
| 複数箇所を同時に変更 | 1箇所ずつ検証 |
| 症状だけ修正（根本原因を無視） | 5-Why で根本原因まで追う |
| 本番でデバッグ | ローカル/ステージングで再現 |
| 修正後テストなし | バグ再現テストを必ず追加 |
| ログを見ずに推測 | ログ・スタックトレースを最初に確認 |
