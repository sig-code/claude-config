# first-review（輪郭レビュー）

diff を1行ずつ読む前に「変更の輪郭」だけを先に見る。精読対象を最初に絞り込むことで、大きな PR でもレビュー速度と精度を両立する。
出典: https://www.m3tech.blog/entry/rinkaku-pr-review

## 手順

1. **全体像の取得**: `git diff --stat`（PR なら `gh pr diff --stat`）で変更ファイル一覧と規模を把握し、依存関係順（エントリポイント → 基盤側）に並べ替える。テスト・自動生成物は後回しにする。
2. **シグネチャ変更の抽出**: 各ファイルで公開関数・メソッド・型・API 契約の追加/変更/削除だけを拾う。実装の中身はまだ読まない。
3. **影響シグナルの評価**: シグネチャが変わったシンボルは Grep で参照元数（fan-in）を数える。「契約変更 × 高 fan-in」が最優先の精読候補。
4. **輪郭レベルの設計スメル確認**:
   - 特定ファイルへの行数・責務の集中（神ヘルパー化）
   - エントリポイントの引数変化（DI・依存の崩れ）
   - 契約変更に対応するテストの有無
5. **精読対象の絞り込み**: 上記から精読が必要な箇所を最大5件に絞り、理由付きで提示する。

## 出力フォーマット

```
## 輪郭サマリ
（1〜3行。変更の性質と規模、パッと見の健全性）

| ファイル | シグネチャ変更 | fan-in | 注意 |
|---|---|---|---|

## 精読推奨（優先順）
1. path/to/file.ts:42 — 理由（例: 戻り値の型変更、参照元12件）

## 輪郭レベルの気づき
- （設計スメル・テスト欠落など。なければ「なし」）
```

このスキルのゴールは精読対象の提示。approve / request-changes の最終判定は、精読（本レビュー）の後に行う。
